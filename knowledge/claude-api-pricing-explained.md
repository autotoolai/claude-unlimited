# Claude API 怎么计费：token 构成与估算

> 正式发布地址：[claude-unlimited.aiautotools.com/knowledge/claude-api-pricing-explained](https://claude-unlimited.aiautotools.com/knowledge/claude-api-pricing-explained) ｜ 源码与文档：[GitHub 仓库](https://github.com/autotoolai/claude-unlimited)

> **一句话答案**：账单 = 输入 token × 输入价 + 输出 token × 输出价。输入 token 包含系统提示、历史对话、检索文档、文件内容、工具定义与工具结果；输出 token 是模型实际生成的文本。两者的单价不同，输出通常贵 5 倍。除了标准输入与输出，缓存读取与缓存写入是单独计价的 2 类，缓存写入还有 5 分钟与 1 小时 2 种 TTL（写入价分别是基础输入价的 1.25 倍和 2 倍，读取价是 0.1 倍），Batch API 对输入与输出打 5 折。一次对话的账单往往远大于你看到的用户输入——用 /cost 可以看一次真实会话的消耗。

大多数人的账单困惑来自一个假设：**我发了 500 字，所以只该收 500 字的费用**。实际账单里，输入那栏可能是你输入的 10 倍，输出那栏又可能是输入的一半。下面把它拆开算。

## 输入 token 包含什么

**结论**：你发给模型的一切都算输入，不只是用户输入的那句话。

- 系统提示与开发者指令、格式规则、安全约束；
- 历史对话（每轮都重发，见[为什么 Agent 比聊天更烧 token](why-agents-cost-more-tokens.md)）；
- 检索到的文档片段（RAG）、上传文件的抽取文本；
- 工具 / 函数定义的 schema（开了缓存则按缓存读写价计）；
- 工具调用的返回结果（JSON 也算）。

**还有一块容易漏掉的：工具本身要额外消耗 token。** 当你传了 `tools`，API 会自动附加一段启用工具使用的系统提示。Opus 5.5、Sonnet 5.5、Haiku 5.5 在 tool_choice 为 `auto` 或 `none` 时各加 **286 个 token**；Claude 4.6 及更早的模型加 497 到 675 个不等。

Bash 工具的定义本身还会再加 **325 个 token**（4.7 及更新的模型；4.6 及更早是 244 个）。这些都计入输入。

## 输出 token 包含什么

**结论**：模型实际生成的文本，以及它生成的工具调用、JSON 对象、代码补丁。

摘要、JSON 生成、代码补丁、Markdown 文档、长篇文案、数据清洗结果、多语言翻译都会产生大量输出 token。给不同场景设置合理的最大输出长度，避免模型在不必要的时候输出长解释。

## 为什么输出往往比输入贵

**结论**：因为输出是模型逐 token 生成、需要算力更多的部分，各档位模型的输出单价通常是输入的 5 倍。

| 模型 | 输入（每百万 token） | 输出（每百万 token） | 倍数 |
|---|---|---|---|
| Claude Fable 5.2 | $8 | $40 | 5× |
| Claude Opus 5.5 | $4 | $20 | 5× |
| Claude Sonnet 5.5 | $2 | $10 | 5× |
| Claude Haiku 5.5 | $0.10 起 | $0.50 起 | 5× |

这带来两个实操结论：长报告、长代码的输出是账单大头，要设上限；简单任务路由到便宜档位时，输出价差被放大，收益比输入价差更明显。

## 缓存与 Batch 的价怎么算

**结论**：除了标准输入与输出，缓存读取与缓存写入是单独计价的两类；Batch API 对输入与输出打 5 折。具体数值以[套餐定价](https://claude-unlimited.aiautotools.com/pricing)页与官方文档为准。

| 计费类别 | 含义 | 倍数（相对基础输入价） |
|---|---|---|
| 标准输入 | 未命中缓存的普通输入 | 1× |
| 标准输出 | 模型生成 | 各模型自己的输出单价 |
| 缓存写入（5 分钟） | 建立短 TTL 缓存的一次性成本 | 1.25× |
| 缓存写入（1 小时） | 建立长 TTL 缓存的一次性成本 | 2× |
| 缓存读取 | 命中提示缓存的输入前缀 | 0.1×（多数模型） |

估算时要把这几类分开，不要用「输入价 × 全部输入」一刀切，否则缓存策略的效果会算不出来。缓存机制见[提示缓存原理：什么时候省钱、什么时候白花](prompt-caching-explained.md)。

### 缓存的倍率因模型而异

**结论**：多数模型缓存读取是基础输入价的 0.1 倍，但新一代模型更便宜。

| 模型 | 缓存读取倍率 | 每百万 token |
|---|---|---|
| Claude Fable 5.2 / Fable 5.1 | 0.025× | $0.20 |
| Claude Opus 5.5 | 0.05× | $0.20 |
| Claude Sonnet 5.5 | 0.05× | $0.10 |
| 其它模型 | 0.1× | 见价目表 |

**缓存读划算的门槛**：5 分钟 TTL 写入价是 1.25 倍，读一次就回本；1 小时 TTL 写入价是 2 倍，**要读两次才回本**。所以长 TTL 缓存只在确实会命中多次时才用。

这些倍率**与其它定价修正可以叠加**，包括 Batch API 折扣和数据驻留。

## 三个容易忽略的额外计费项

**结论**：除了输入输出和缓存，还有三处会让账单偏离你的预期。

### 长上下文

Claude 4.6 及之后的模型（Haiku 5.5 除外）**整个 100 万 token 窗口都是标准价**——90 万 token 的请求和 9000 token 的请求单价一样。缓存与 Batch 折扣在整个窗口内都照常生效。

例外是 **Haiku 5.5 按提示长度定价**：提示超过 **10 万 token** 的请求按更高价计。提示长度包含所有输入 token（缓存读写都算），而且**每个请求独立计价**——超阈值的那个请求即使部分命中缓存也按高价算，之前的请求保持原计价。

### 工具使用

工具调用的请求按三部分计价：发送给模型的总输入 token（含 `tools` 参数）、生成的输出 token、以及服务端工具的额外按次计费（比如 web search 按搜索次数收费）。

客户端工具和普通请求同价，但服务端工具有额外费用。

### 数据驻留与 fast mode

- **数据驻留**：`inference_geo: "us"` 对所有 token 类别（输入、输出、缓存写、缓存读）施加 **1.1 倍**系数。全局路由（默认）用标准价。
- **fast mode**：输出速度最高提升 2.5 倍，价格更贵。Claude Fable 5.2 是 $8/$40（相对标准价），Claude Opus 5.5 是 $8/$40，Claude Opus 5 与 4.8 是 $10/$50。fast mode **不能与 Batch API 同用**。

## 按量、订阅还是固定费率

**结论**：Pro/Max 订阅是「聊天产品附带一点 API」，按 token 计费的 API 是「纯调用通道」，固定费率不限量是「周期内不按 token 计费」。三者不是谁更便宜，而是适合谁。

| 方式 | 本质 | 你得到什么 | 适合谁 |
|---|---|---|---|
| **Pro / Max 订阅** | 消费级产品 | claude.ai 聊天界面、对话历史、文件上传，外加一定额度的 API 与 Claude Code 用量 | 主要在浏览器里用 Claude |
| **按 token 计费 API** | 用量付费 | HTTP 接口，用多少算多少 | 程序化调用，用量小或波动大 |
| **固定费率不限量** | 周期套餐 | 订阅期内不按 token 计费 | 每天跑 Claude Code 跑长任务、处理大代码库或多个子代理 |

**结论**：Pro/Max 的 API 与 Claude Code 用量是「附带的」，不是「为主的」。它按 token 而不是按消息消耗，带子代理的长会话掉得很快，重度用户常在计费周期前几天就用完。额度用完只能等重置或额外接 API，见[Claude 提示用量上限：分清是哪个计量器](claude-code-usage-limit-reached.md)。

**结论**：「不限量」取消的是按 token 计费，不是无边界。套餐按「同时可开几个会话窗口」区分，也不包含生产流量与压测（怎么选见[常见问题](https://claude-unlimited.aiautotools.com/faq#cat-limits-speed)）。取消的是计费压力，不是使用边界。

判断依据很简单，不用心算「这次大概多少 token」就选固定费率；如果一周只调用几次、每次规模可预测，按量更省：

- 主要在网页聊天，偶尔调 API：Pro 或 Max。
- 每天写代码，Claude Code 只是辅助：Max 的附带额度可能够。
- 每天用 Claude Code 跑长任务、大代码库、多个子代理：固定费率不限量。
- 用量小、波动大、需要精确控制每次调用成本：按 token 计费。

接入方式（Base URL + Key）三种都一样，换计费方式不用换配置，见[套餐定价](https://claude-unlimited.aiautotools.com/pricing)。

## 四步估算一个月要花多少

**结论**：不要从理想化的 prompt 开始估算，从真实任务样本开始。

### 1. 收集代表性样本

一条带上下文的工单、一次代码库问答、一次文档分析、一次多轮对话、一次 JSON 抽取、一次 Claude Code 修复任务。

### 2. 估算每类样本的输入与输出 token

可以用 `/cost` 看一次真实会话的消耗，或在响应里读 usage 对象。

### 3. 乘以单价

```text
月成本 ≈ Σ（每类样本的输入 token × 输入价 + 输出 token × 输出价）× 每月调用次数
```

要更准就把缓存和 Batch 单独列出来：

```text
月成本 ≈ Σ[
  (标准输入 token × 输入价)
  + (缓存写入 token × 写入倍率 × 输入价)
  + (缓存读取 token × 读取倍率 × 输入价)
  + (输出 token × 输出价)
] × 每月调用次数
```

### 4. 同时估平均与重度

**结论**：中位数往往便宜，但 top 5% 的请求（大文件、长对话、复杂工具链、反复重试、超长输出）决定账单是否可预测。只看平均会低估峰值。

产品形态决定了这两种估算都重要：知识库问答里大多数用户只问简单问题，少数会上传几十页文档连续追问；代码助手里大多数请求只是解释函数，少数要求跨项目重构。

## 一个 tokenizer 版本变化带来的坑

**结论**：Claude 4.7 及之后的模型（以及 Mythos Preview）使用新的 tokenizer，**同一段文本大约多出 30% 的 token**，具体增幅取决于内容和工作负载形态。Claude Sonnet 4.6 及更早的模型用旧 tokenizer。

所以用旧模型的 token 数估算新模型的账单，会系统性低估约 30%。跨代升级时要按新 tokenizer 重新测一遍，而不是沿用历史样本。

## 让估算更准的几个动作

**结论**：估算不准通常不是单价算错，而是用量没有被约束。按这 8 条做：设用量上限、设超时与重试、给重复输入开缓存、长文档分块检索、给 agent 循环设步数上限、区分可重试错误、批量任务走 Batch API、换模型后重测 token 数。

- 给每个用户 / 工作区 / Key 设用量上限；
- 给请求设超时、最大重试次数、最大输出长度；
- 对重复输入开缓存；
- 对长文档分块与向量检索，别整篇塞进去；
- 给 agent 循环设步数上限；
- 区分可重试与不可重试错误，避免无意义循环；
- 可延迟的批量任务走 Batch API，直接省一半；
- 换新代模型时重新测 token 数，别沿用旧 tokenizer 的样本。

## 实战案例

**结论**：账单比直觉贵的原因不是模型单价，而是每轮都重发的上下文。三个案例分别对应三类常见误解：单次交互其实很贵、批处理可以直接打 5 折、缓存策略决定固定前缀要付几次钱。

### 案例 1：一次 Claude Code 会话为什么比想象贵

用户输入：「修一下这个测试」，看上去 10 个字。实际账单里输入可能是 8 万 token：

- 系统提示 + CLAUDE.md + 技能描述：几千 token；
- 工具定义（每个工具的 schema + 那 286 token 的工具系统提示）：几千 token；
- 它读进来的 20 个文件内容：几万 token，且**此后每一轮都重发**；
- 历史对话本身：每轮累积。

输出则是它写出的补丁和解释，通常是输入的几分之一。

### 案例 2：把批处理挪到 Batch API

分类、抽取、回填这类可延迟的任务改走 Batch API，输入输出都打 5 折。Haiku 5.5 的批量输入低至 $0.05/MTok、输出 $0.25/MTok。

### 案例 3：缓存策略怎么定

固定的系统提示 + 工具定义 + 大段参考文档放最前面，用 5 分钟 TTL；如果同一份文档会在一小时内被反复用，改用 1 小时 TTL，但记得它要读两次才回本。

## 怎么选（决策矩阵）

**结论**：按「成本占比在哪一栏」和「能不能延迟」两个维度决定优化动作。

| 你的情况 | 主要成本 | 该做什么 |
|---|---|---|
| 输入远大于输出 | 上下文重发 | 开缓存、把稳定前缀前置、限制读文件范围 |
| 输出远大于输入 | 生成量大 | 设最大输出长度、降档位 |
| 两者都大 | 上下文本身太重 | 换更省 token 的架构：子代理、检索替代整篇塞入 |
| 调用量巨大但可延迟 | 全部 | 走 Batch API 打 5 折 |
| 提示频繁重复 | 缓存读写 | 5 分钟 TTL 写入，命中一次就回本 |
| 同一文档一小时内多次用 | 缓存读写 | 1 小时 TTL，但要读两次才回本 |
| 升级到 4.7+ 新模型 | 全部 | tokenizer 多约 30% token，重新测样本 |
| 提示超 10 万 token | 输入 | 注意 Haiku 5.5 按提示长度分档计价 |

## 最佳实践

**结论**：账单优化按「先降单价、再降 token 数」两步做。

1. **先降单价**：简单任务下沉到 Haiku、延迟任务走 Batch、常规请求命中缓存。
2. **再降 token 数**：限制上下文、拆子代理、检索替代整篇输入。
3. **设上限**：每个 Key、每个用户、每个请求都要有上限和超时。
4. **看真实账单**：用 `/cost` 和 usage 对象，别用估算值代替实际值。
5. **换代重测**：tokenizer 变了，历史样本就不能直接用了。
